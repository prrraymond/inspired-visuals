# ChartGen / DataViz — Restart Audit

**Date:** 2026-09-12
**Scope:** Orientation only. No code was written, edited, or refactored.
**Method:** Read every script in `Scripts/`, diffed working tree against `HEAD`, and ran
read-only live probes against the Anthropic, Notion, and Supabase endpoints configured in
`.env.local`. No pipeline script was executed. Findings marked **[inferred]** were not read
directly from code or verified against a live service.

**Headline:** the PRD names three Phase 0 blockers. One is real, one is real but misdescribed,
one is materially wrong — and none of them is the blocker that actually stops the pipeline.
The Supabase project the entire asset layer depends on no longer resolves in DNS.

## 2. What's broken

Ordered by what actually blocks a restart, not by the PRD's ordering.

### B0 — The Supabase project does not resolve *(not in the PRD; this is the real blocker)*

```
DNS: supabase.co            → 76.76.21.21     OK
DNS: api.supabase.com       → 104.18.42.230   OK
DNS: <project>.supabase.co  → NXDOMAIN
```

Every other host tested resolves. A *paused* free-tier Supabase project keeps its DNS record
and answers with a pause notice; a project whose subdomain has stopped resolving has been
deleted or reaped. **[inferred — the distinction between "deleted" and "reaped" can only be
settled in the Supabase dashboard; the non-resolution itself is verified.]**

What this takes down:

- All 724 `Base Code URL`s in the Code Templates DB — the 507 public ones and the
  217 signed-to-2030 ones alike. Expiry is irrelevant when the host is gone.
- All `Asset URL` / `Thumbnail` values across all three databases (1,048 + 1,301 = **2,349** URLs).
- Stage A (reads the bucket), Stage C (uploads code), Stage D (uploads datasets, code,
  and renders, and runs SQL against `SUPABASE_DB_URL` on the same host).
- Every chart image the Claude vision call needs as input.

**Recovery paths that survive.** Full generated code is still retrievable from Notion: each of
the 507 code-bearing rows carries a `code` child block holding the complete script
(spot-checked 6 rows: 2.3 K–5.3 K chars each, versus the 1,800-char truncated `Source code`
property). Plus the 253 local files in `generated/plotly/`. The source chart **images** have no
local copy and are not recoverable if the bucket is gone.

### B2 — Rendering is **not** a stub, and kaleido works here

The PRD's top-priority blocker describes code that was archived a year ago.

- `Scripts/archive/hydrate_viz_library.py:341-349` — this is the stub. Prints
  `"Skipping chart image generation (kaleido configuration needed)"`, returns `None`.
- `Scripts/hydrate_viz_library_v3.py:182-198` — the **live** script. Fully implemented:
  `exec()`s the generated code with a `load_csv` helper injected, finds the `Figure` in the
  namespace, calls `fig.to_image(format="png", scale=2)`, uploads to
  `charts/{cid}/{cid}_chart.png`. Identical implementation in `hydrate_viz_library_v2.py:182-201`.

Verified on this machine: Python 3.11.13, `plotly` 6.0.1, `kaleido` 0.2.1.
`pio.kaleido.scope` resolves; PNG export returns 43,675 bytes; **SVG export also works**
(5,317 bytes) though no script requests SVG.

So R1 is not "resolve the kaleido dependency." Kaleido is installed and functional. The reason
no renders exist is that Stage D has never completed a run — because of B0, B1, and B5, not
because of the renderer. Note that `kaleido` 0.2.1 with `plotly` 6.x is a supported-but-aging
pairing; kaleido ≥1.0 removed `pio.kaleido.scope`, so `hydrate_viz_library_v3.py:30` will raise
`AttributeError` at import if kaleido is ever upgraded. **[inferred — not tested, since 0.2.1
is what's installed.]**

### B3 — Signed URLs: the described expiry does not exist

The PRD predicts catalog death on 2026-09-24. Actual state, by decoding the `exp` claim of
every signed URL in all three databases:

| Database | Property | Public | Signed → expiry |
|---|---|---|---|
| Code Templates | `Base Code URL` | 507 | 217 → **2030-10** |
| Code Templates | `Thumbnail` | 0 | 253 → **2026-09** |
| Assets (v2) | `Asset URL` | 200 | 449 → **2026-09** |
| Assets (v2) | `Thumbnail` | 200 | 449 → **2026-09** |
| Production | `Asset URL` | 399 | 0 |
| Production | `Thumbnail` | 399 | 0 |

The 1,151 URLs expiring this month are **source chart images and thumbnails**, not code. The
code URLs the PRD worried about are either public (no expiry) or signed for five more years —
`generate_base_code_v2.py:45` sets `SIGNED_URL_TTL = 31536000 * 5`.

The impact is the inverse of what the PRD says: losing image URLs breaks **re-running Stage C**
(the vision call needs the source image), not reading existing code. All of which is academic
while B0 stands — none of these URLs resolve today regardless of their tokens.

Where URLs are minted:
`generate_base_code.py:261-271` (tries `get_public_url`, falls back to `create_signed_url`),
`generate_base_code_v2.py:119`, `hydrate_viz_library_v2.py:120`, `hydrate_viz_library_v3.py:120`,
`bootstrap_supabase_to_notion_v2.py:195,299` (public only), `export_images_to_storage.py:65`.
Where they are persisted: Notion `url` and `files` properties only. **There is no local index
of storage keys.** Rebuilding URLs after a bucket restore means re-deriving keys from `chartid`
by convention, because nothing records the mapping.

### B4 — `generate_base_code.py` writes a property the target DB doesn't have

`create_target_page()` at line 293 writes `"Base code URL"`. The live Code Templates DB
property is **`Base Code URL`** (capital C). Notion property names are case-sensitive; an
unknown name is a 400. Every Stage C page creation fails at this call — after the LLM spend.

Related mismatches in the same function: it writes Status `"draft"` where existing rows use
`"Draft"` (Notion will silently create a second select option), and it no longer writes
`Data contract` at all (see B8).

### B5 — Stage C and Stage D are not connected, and Stage D targets a status that doesn't exist

Two independent wiring faults:

1. **Base code is written to the wrong database.** Both Stage C scripts write `Base Code URL`
   into the **Code Templates** DB. `hydrate_viz_library_v3.py:238` reads `base_code_url` from
   the **Production** DB, where — verified live — **0 of 400 rows** have that property set.
   Stage D would proceed with `base_code = "# No base code provided."` and ask the LLM to
   generate final code from nothing. The two halves of the pipeline have never been joined.

2. **`STATUS_COMPLETE` names a non-existent option.** `hydrate_viz_library_v3.py:45` defaults to
   `"4. Complete"`. The live Production DB's Status options are:
   `1. Intake`, `2. In progress`, `3. Needs hydration`, `4. Hydrated`, `Needs Review`, `5. Complete`.
   There is no `4. Complete`. The terminal `requests.patch` would 400 — and because that patch
   is fired with `requests.patch(...)` and its response is never checked, the script would
   print `UPDATED {chartid}` and exit 0 having written nothing.

   Also note the corpus this stage can even see: exactly **1** row sits at `3. Needs hydration`.

### B6 — `export_images_to_storage.py` raises `NameError` on every upload

`SUPABASE_PUBLIC_BASE` is referenced at line 62 but its definition is commented out at line 26.
`SupabaseDriver.upload_png()` cannot complete. `--dry-run` never reaches it, which is likely
why this survived.

### B7 — 249 duplicate rows in the Code Templates DB

724 rows over 475 distinct `chartid`s: 249 chartids appear exactly twice, 226 once.
Root cause is visible in `generate_base_code.py:281-286` — `target_page_exists()` wraps its
Notion query in `except Exception: return None`, so any transient API error is indistinguishable
from "no existing row" and produces a duplicate. `generate_base_code_v2.py` builds its dedupe
index differently (`existing_templates` keyed on `chartid`) against the same table, so running
both scripts also duplicates. **[inferred — the 249 = "one row per script" hypothesis fits the
217-row no-status cohort and the 507-row coded cohort, but I did not diff row creation timestamps.]**

### B8 — `data_contract` was deleted from the working tree

This is the single most consequential uncommitted change, and it inverts a PRD requirement.

`git HEAD:Scripts/generate_base_code.py` had:
```python
class ClaudeOut(BaseModel):
    plotly_code: str
    filename_suggestion: Optional[str] = None
    notes: Optional[str] = None
    data_contract: Optional[Dict[str, Any]] = None
    caveats: Optional[List[str]] = None
```
The working tree (−551/+213 lines) has:
```python
class ClaudeOut(BaseModel):
    plotly_code: str
    filename_suggestion: Optional[str] = None
    notes: Optional[str] = None
    # data_contract is removed as we are now generating abstract templates
    caveats: Optional[List[str]] = None
```

The prompt changed to match, and in the opposite direction from the PRD's description:

| | Committed (what the PRD describes) | Working tree (what exists) |
|---|---|---|
| Data | "complete inline pandas DataFrame with realistic column names and ~20–50 rows" | "**Do NOT** create an inline pandas DataFrame or use hard-coded data" |
| Shape | Runnable script, `fig.show()` | Abstract `build_figure(df)` with `x_column` placeholders |
| Output keys | 5, incl. `data_contract` | 4 |

`data_contract` now appears in exactly one place in the entire repo — that comment. All 253
existing contracts came from the committed version. **Nothing in the working tree can produce
another one.** Meanwhile all 253 local templates in `generated/plotly/` are old-style
(236 contain `pd.DataFrame`, 0 contain `build_figure`), which means the rewritten script has
never produced a stored artifact.

There is a genuine design tension here that the PRD doesn't acknowledge: the abstract-template
rewrite and the data-contract requirement pull in opposite directions. An abstract
`build_figure(df)` template with placeholder column names has no concrete schema to contract
against — which is arguably *better* for R10 (bring-your-own-data), since the user's columns map
onto placeholders rather than having to match a fabricated sample. **This needs a decision
before any Phase 1 work, not a bug fix.**
